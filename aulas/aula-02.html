Objetivos de aprendizagem

Ao fim desta aula você será capaz de:

  • Comparar os modelos hierárquico, em rede, relacional e NoSQL, dizendo o que cada um resolve.
  • Usar corretamente relação, tupla, atributo, domínio, grau e cardinalidade, ligando cada termo ao seu equivalente em SQL.
  • Explicar os três esquemas da arquitetura ANSI/SPARC e o que cada um esconde do nível de cima.
  • Distinguir modelo conceitual, lógico e físico apresentando o mesmo trecho do modelo nos três níveis.
  • Classificar um comando SQL em DDL, DML, DQL, DCL ou TCL.

Problematização

Na aula anterior ficou decidido que a Bella Massa precisa de um banco de dados. Falta uma pergunta que quase ninguém faz e que muda tudo: banco de dados de que tipo? "Relacional" é uma escolha, não uma lei da natureza. Existiram modelos antes dele e existem modelos depois, e alguns deles resolveriam partes deste problema melhor.

Esta aula ainda é de quadro. Ela responde três coisas: por que o modelo relacional venceu, qual é o vocabulário exato que você vai usar nos próximos 22 encontros, e por que a mesma base de dados é descrita em três níveis diferentes — o que o atendente vê, o que você desenha e o que o disco guarda.

A evolução dos modelos de dados

Um modelo de dados é o conjunto de conceitos usados para descrever a estrutura de um banco: que formas os dados podem ter e como se ligam. Cinco famílias importam para a sua formação:

Modelo Época Como organiza Limite que motivou o sucessor
Hierárquico Anos 1960 (IMS, IBM) Árvore: cada registro tem um pai só Não representa "muitos para muitos" sem duplicar dados
Em rede Anos 1970 (CODASYL) Grafo de ponteiros entre registros A consulta precisa saber o caminho físico; mudar a estrutura quebra os programas
Relacional 1970 (Codd) Tabelas ligadas por valor, não por ponteiro Encaixa mal dados sem esquema fixo e escala horizontal difícil
Orientado a objetos Anos 1990 Objetos com identidade, herança e métodos Baixa adoção; sobreviveu como recurso dentro dos relacionais
NoSQL A partir de 2009 Documento, chave-valor, coluna larga ou grafo Abre mão de parte da consistência e da integridade declarada

A diferença fica clara com um exemplo. Um pedido da Bella Massa, com cliente e itens, no modelo hierárquico é uma árvore: tudo pendurado no pedido.

Funciona para ler um pedido. Quebra na segunda pergunta do negócio: quais pedidos a Helena já fez? Como o cliente vive dentro de cada pedido, ele está repetido em todos eles — a mesma redundância da planilha, agora com nome de modelo. E se ela trocar de telefone, é preciso percorrer a árvore inteira.

No modelo relacional, cliente e pedido são coisas separadas que se ligam por um valor em comum. Ninguém está dentro de ninguém:

A Helena aparece uma vez em cliente e é referenciada duas vezes em pedido, pelo valor 1. Trocar o telefone dela é alterar uma linha. Essa ideia — ligar por valor, não por ponteiro — é a contribuição central do modelo relacional.

NoSQL não é o "próximo" modelo

É uma família de alternativas para problemas específicos: catálogo com campos que variam por produto (documento), sessão de usuário (chave-valor), rede de amigos (grafo). Nenhuma delas substitui o relacional em um sistema com transações e regras de integridade, que é exatamente o caso de uma pizzaria com pagamento. O encontro 24 fecha o curso com esse comparativo — e você vai chegar lá sabendo o que está comparando.

O modelo relacional de Codd

Em 1970, Edgar F. Codd, matemático da IBM, publicou A Relational Model of Data for Large Shared Data Banks. A proposta era radical para a época: descrever os dados usando teoria dos conjuntos e lógica de predicados, e proibir que o programa soubesse como eles estavam guardados.

Princípio O que significa Consequência prática no curso
Tudo é relação Só existe uma estrutura de dados: a relação (tabela) Não há registro "dentro" de outro; hierarquia vira chave estrangeira
Acesso por conteúdo Uma linha é encontrada pelo valor dos seus atributos, nunca por endereço WHERE id_cliente = 1, e não "o terceiro registro do arquivo"
Independência física Como os dados estão gravados não afeta como são consultados Criar um índice no encontro 21 não muda uma linha das suas consultas
Integridade declarada As regras ficam no banco, não espalhadas nos programas Uma CHECK vale para o sistema, para o SSMS e para o estagiário
Linguagem de conjuntos Você descreve o resultado desejado, não o algoritmo de busca SQL é declarativa: quem decide o caminho é o otimizador
Declarativo, não procedural

Em uma linguagem procedural você escreveria: "abra o arquivo, leia linha a linha, compare o campo 3, guarde os que baterem". Em SQL você escreve o que quer — SELECT nm_cliente FROM cliente WHERE id_cliente = 1 — e o SGBD decide se usa índice, em que ordem lê e quanta memória gasta. É por isso que a mesma consulta fica mais rápida quando você cria um índice, sem trocar uma vírgula dela.

Relação, tupla, atributo, domínio e chave

Cada conceito tem três nomes: o formal (da teoria de Codd), o do SQL e o coloquial de quem veio de arquivos. A banca usa o formal; o produto usa o do SQL. Saiba os dois.

Formal Em SQL Coloquial Definição
Relação Tabela Arquivo Conjunto de tuplas com a mesma estrutura
Tupla Linha Registro Uma ocorrência: um cliente, um pedido
Atributo Coluna Campo Uma propriedade da entidade
Domínio Tipo + CHECK Formato O conjunto de valores que o atributo pode assumir
Grau Nº de colunas — Quantos atributos a relação tem
Cardinalidade Nº de linhas — Quantas tuplas a relação tem neste momento
Chave primária PRIMARY KEY Código Atributo (ou conjunto) que identifica cada tupla sem ambiguidade

Aplicando na relação cliente mostrada acima: ela tem grau 3 (três atributos) e cardinalidade 2 (duas tuplas). O domínio de id_cliente são os inteiros positivos; o de nm_cliente, textos de até 120 caracteres. E a chave primária é id_cliente.

Duas cardinalidades diferentes

A palavra cardinalidade aparece em dois contextos nesta unidade, com sentidos distintos. Aqui, cardinalidade de uma relação é a quantidade de linhas que ela tem agora — muda a cada INSERT. No encontro 06, cardinalidade de um relacionamento é a regra 1:1, 1:N ou N:N — e não muda nunca, porque é parte do modelo. Quando alguém disser só "cardinalidade", pergunte de qual das duas se trata.

Arquitetura ANSI/SPARC em três esquemas

Em 1975 o comitê ANSI/SPARC propôs separar a descrição de um banco em três níveis. A ideia organiza até hoje a arquitetura de qualquer SGBD relacional, e explica por que o atendente da pizzaria, você e o disco enxergam a mesma base de três formas diferentes.

Nível Descreve Quem se importa Na Bella Massa
Externo (visão) O recorte que cada grupo de usuários enxerga Usuário final e aplicação Uma VIEW com nome e telefone, sem valores nem custos
Conceitual (lógico) Todas as entidades, atributos, relacionamentos e regras Projetista do banco — você As 17 tabelas, com chaves e restrições
Interno (físico) Como os dados são gravados: arquivos, páginas, índices SGBD e DBA bellamassa.mdf, bellamassa.ldf e os índices

O ponto da arquitetura não é a existência dos três níveis: é o isolamento entre eles. Cada nível esconde do nível de cima as decisões que tomou.

Independência de dados

É o benefício concreto que os três esquemas entregam, e vem em duas formas. Guarde os dois nomes: eles caem em prova e explicam metade das boas práticas do curso.

Tipo Definição Exemplo na pizzaria
Independência física Mudar o nível interno não afeta o conceitual nem o externo Criar um índice em dt_pedido, ou mover o .mdf para outro disco: nenhuma consulta muda
Independência lógica Mudar o nível conceitual não afeta as visões existentes Acrescentar a coluna fl_vegana em produto: a tela do atendente continua funcionando

A independência lógica é a mais difícil de conseguir e a que mais se perde na prática — basta uma aplicação escrever SELECT * para que acrescentar uma coluna quebre a tela. Este é o primeiro motivo, entre vários, para nunca usar SELECT * em código de produção; o encontro 16 volta ao assunto.

Conceitual, lógico e físico

Projetar um banco é descer uma escada de três degraus. O mesmo pedaço de realidade é descrito três vezes, cada vez com mais compromisso técnico. Veja a entidade cliente nos três degraus.

Degrau 1 — modelo conceitual

Fala a língua do negócio. Não menciona tipo de dado, tamanho de coluna nem produto de SGBD. A notação clássica é a de Chen: retângulo para entidade, elipse para atributo, atributo identificador sublinhado. É o que você vai desenhar nos encontros 05 a 07.

Degrau 2 — modelo lógico

Já assume o modelo relacional: tudo vira tabela, chave primária e chave estrangeira. Ainda não escolhe o SGBD, mas escolhe a estrutura. A notação usual é a pé-de-galinha, e é o que os encontros 08 a 10 produzem.

Degrau 3 — modelo físico

Aqui entra o produto. Tipos do T-SQL, tamanhos, valores padrão, nomes de constraint, IDENTITY. O mesmo cliente, agora em código que o SQL Server 2022 executa — é o que você escreverá no encontro 13.

A escada só desce

Do conceitual para o físico existe um caminho: são as sete regras de mapeamento do encontro 09. Do físico de volta para o conceitual não existe caminho automático — por isso um banco criado sem modelo nunca produz um diagrama honesto depois. É a versão técnica do erro "começar pelo CREATE TABLE" que a aula 01 apontou.

DDL, DML, DQL, DCL e TCL

SQL é uma linguagem só, dividida por função em sublinguagens. Saber a qual grupo um comando pertence antecipa o comportamento dele — sobretudo se a ação pode ou não ser desfeita por um ROLLBACK.

Sigla Nome Comandos Mexe em Encontro
DDL Data Definition Language CREATE, ALTER, DROP, TRUNCATE Estrutura 13 e 14
DML Data Manipulation Language INSERT, UPDATE, DELETE, MERGE Conteúdo 15
DQL Data Query Language SELECT Nada — só lê 16 a 21
DCL Data Control Language GRANT, REVOKE, DENY Permissões 24
TCL Transaction Control Language BEGIN TRAN, COMMIT, ROLLBACK Limites da transação 15 e 24

Um comando de cada, para você reconhecer a família pela forma. Todos rodam a partir do encontro 13; aqui servem de referência visual:

O ROLLBACK acima desfez o UPDATE

Depois daquele bloco, a forma de pagamento continua gravada como PIX, e não Pix: a transação foi desfeita. No SQL Server — diferente de alguns outros SGBDs — DDL também é transacional, então um CREATE TABLE dentro de uma transação desfeita também some. É um detalhe do produto que o encontro 15 explora.

O nível interno: .mdf e .ldf

O nível mais baixo do ANSI/SPARC tem nome de arquivo. Todo banco no SQL Server ocupa no mínimo dois:

Arquivo Extensão Guarda Se você perder
Dados primário .mdf Tabelas, índices, metadados e as próprias definições do banco Perde tudo que não estiver em backup
Log de transações .ldf O registro sequencial de toda alteração, antes de ela ser aplicada Perde a capacidade de desfazer e de recuperar até um instante
Dados secundário .ndf Opcional: parte dos dados, em outro disco, para distribuir carga Perde as tabelas que moravam nele

Dentro do .mdf, o dado não fica solto: é organizado em páginas de 8 KB, agrupadas em extents de oito páginas (64 KB). Uma linha não pode atravessar páginas, e é daí que vem o limite prático de 8.060 bytes por linha — um número que reaparece no encontro 13, quando você escolher entre VARCHAR(8000) e VARCHAR(MAX).

Quem responde onde esses arquivos estão é o próprio banco. Esta consulta é a que você vai executar de verdade na próxima aula, depois de instalar a instância:

Nunca copie um .mdf com o serviço no ar

Copiar os arquivos de um banco ligado não é backup: o resultado é um arquivo inconsistente e inútil, porque parte das alterações ainda está só no log. Backup se faz com o comando BACKUP DATABASE, e é assunto do encontro 24 — indicador 5.

Diga a qual sublinguagem pertence cada comando e o que ele afeta:

  1. ALTER TABLE produto ADD fl_vegana BIT NOT NULL DEFAULT 0;
  2. SELECT nm_produto FROM produto WHERE fl_vegana = 1;
  3. REVOKE SELECT ON dbo.pagamento FROM app_bellamassa;
  4. UPDATE produto SET fl_vegana = 1 WHERE id_produto = 12;
  5. COMMIT TRANSACTION;
Ver gabarito
  1. DDL — muda a estrutura da tabela, acrescentando uma coluna.
  2. DQL — apenas lê; nada no banco é alterado.
  3. DCL — retira uma permissão de um usuário.
  4. DML — altera o conteúdo de uma linha.
  5. TCL — confirma a transação aberta, tornando as alterações definitivas.

Observe a relação abaixo e responda: qual é o grau, qual é a cardinalidade, qual é provavelmente a chave primária e qual o domínio de qt_fatias?

Ver gabarito
  • Grau 3 — três atributos.
  • Cardinalidade 4 — quatro tuplas neste momento. Cadastrar um quinto tamanho muda esse número; o grau só mudaria com um ALTER TABLE.
  • Chave primária: id_tamanho. Note que nm_tamanho também identifica cada linha sem ambiguidade — ele é uma chave candidata, e o encontro 05 trata dessa distinção.
  • Domínio de qt_fatias: inteiros positivos, na prática entre 4 e 12. No banco isso vira TINYINT mais uma restrição CHECK (qt_fatias BETWEEN 1 AND 24).

Para cada mudança, diga qual nível é alterado e quais níveis ficam protegidos:

  1. O DBA move o arquivo bellamassa.mdf para um SSD.
  2. Você acrescenta a coluna fl_vegana na tabela produto.
  3. O atendente passa a ver também o bairro do cliente na tela dele.
  4. Você cria um índice em pedido(dt_pedido).
Ver gabarito
  1. Interno. Conceitual e externo intactos — é independência física funcionando.
  2. Conceitual. As visões existentes continuam válidas, desde que nenhuma use SELECT *: é a independência lógica.
  3. Externo. Só a visão muda; a estrutura das tabelas continua a mesma, porque o bairro já estava lá.
  4. Interno. Nenhuma consulta precisa ser reescrita — elas só ficam mais rápidas.

Na planilha da Bella Massa, para saber os pedidos da Helena o atendente precisa lembrar que "os pedidos dela começam na linha 1.204 da aba de março". Qual princípio do modelo relacional está sendo violado, e qual seria a consequência de mudar a ordem das linhas?

Ver gabarito

Violado: o acesso por conteúdo. No modelo relacional uma tupla é localizada pelo valor dos seus atributos (WHERE id_cliente = 1), e nunca pela posição em que está guardada.

Consequência: ordenar a planilha por outra coluna invalida todo conhecimento acumulado sobre "onde as coisas estão". Numa relação isso é irrelevante, porque uma relação é um conjunto — não tem ordem. É por isso que, no encontro 16, você vai aprender que um SELECT sem ORDER BY não tem ordem garantida, mesmo quando parece ter.

Erros comuns

Conceito Trocar as duas cardinalidades

Perguntado sobre a cardinalidade da relação tamanho, o aluno responde "1:N". Misturou dois conceitos: cardinalidade de relação é a contagem de tuplas — aqui, 4. A cardinalidade 1:N pertence a um relacionamento entre duas entidades e é assunto do encontro 06.

Correção: antes de responder, veja o que a pergunta tem por sujeito. Se é uma tabela, cardinalidade é um número de linhas. Se são duas tabelas ligadas, é 1:1, 1:N ou N:N.
Conceito Achar que uma view guarda dados

A visão do atendente parece uma tabela, então o aluno conclui que os dados foram copiados para lá. Não foram: uma VIEW comum é apenas uma consulta guardada com nome. Ela vive no nível externo e lê, em tempo real, o nível conceitual.

A exceção é a view indexada, que materializa o resultado em disco — e por isso mesmo tem uma lista de restrições, tratada no encontro 21.

Correção: pense na view como uma janela, não como uma gaveta. Se o dado mudar na tabela, a janela mostra o novo valor no próximo SELECT, sem que nada tenha sido copiado.
Msg 208 Esquecer em qual banco o esquema conceitual vive

O nível conceitual pertence a um banco, não à instância inteira. Uma tabela criada em BELLAMASSA não existe no master. Como o sqlcmd e o SSMS abrem conectados ao master, o erro aparece na primeira consulta de todo curso.

Correção: comece todo script com USE BELLAMASSA; seguido de GO, e confirme com SELECT DB_NAME();. Todos os scripts deste site fazem isso na primeira linha, e não por estilo.
Conceito Classificar o SELECT como DML

Muitos materiais — inclusive a documentação de alguns produtos — colocam o SELECT dentro da DML, já que ele "manipula" dados. Outros o separam em DQL, porque ele é o único comando que não altera nada. As duas classificações circulam, e a divergência já derrubou aluno em prova.

Correção: este curso usa DQL para o SELECT, porque a distinção entre ler e escrever é justamente a que importa para permissões (DCL) e transações (TCL). Se a questão não oferecer DQL como alternativa, marque DML e saiba por quê.
