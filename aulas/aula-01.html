Problematização

A Pizzaria Bella Massa fechou 2025 com 38 pedidos por noite anotados em bloco de papel e uma planilha que a gestora chama de "o arquivo". Duas vezes por semana alguém liga perguntando o endereço de um cliente antigo e a resposta demora cinco minutos. O contador pediu o total vendido por sabor no último trimestre e ninguém conseguiu responder.

Você foi chamado para resolver isso. E a primeira decisão profissional que você vai tomar não é qual banco instalar: é entender o que precisa ser guardado, como os dados se relacionam e por que uma planilha não aguenta esse problema. É disso que trata este primeiro encontro — inteiro no quadro, sem computador ligado.

O que é a UC10

UC é unidade curricular: um bloco de competência com começo, meio e avaliação próprios dentro da Habilitação Profissional Técnica em Informática. A UC10 se chama Desenvolver banco de dados e tem 72 horas, distribuídas em 24 encontros de 3 horas.

A competência que ela desenvolve, em uma frase: projetar, implementar, consultar e manter um banco de dados relacional a partir dos requisitos de um cliente. Repare nos quatro verbos — eles não são sinônimos e nenhum deles é "saber SQL de cor".

Implementar Criar banco, tabelas, chaves e restrições em T-SQL; povoar com dados reais Módulo 2

A ordem não é acidental

O módulo de modelagem vem antes do de SQL, e é o mais longo. O motivo é simples: modelo errado não se conserta com SQL bom. Uma consulta ruim você reescreve em dez minutos; uma tabela mal modelada já tem, quando o erro aparece, cinquenta mil linhas de dados apoiadas nela.

Os cinco indicadores, um a um

O plano de ensino da UC10 define cinco indicadores. Eles não são temas: são comportamentos observáveis que você precisa demonstrar. Toda aula deste site declara, no cabeçalho, quais indicadores ela atende — e a tabela abaixo é montada a partir dessa mesma informação, então ela nunca fica desatualizada em relação à trilha.

Leia a coluna do meio como um enunciado de prova prática. "Elabora diagramas de acordo com os requisitos levantados" quer dizer que o seu DER será conferido contra a entrevista da aula 04 — não contra um gabarito genérico de pizzaria. "Desenvolve scripts coerentes com o modelo" quer dizer que o seu CREATE TABLE precisa ser a tradução fiel do seu próprio diagrama.

Onde os alunos perdem nota

Quase nunca é no indicador 3 (scripts SQL). É no indicador 1, quando o diagrama entregue não corresponde ao banco criado, e no indicador 5, quando o projeto chega ao fim sem plano de backup nenhum. Os dois são fáceis de garantir e fáceis de esquecer.

O projeto integrador: Pizzaria Bella Massa

O curso inteiro gira em torno de um caso só. Nada de tabela1, foo ou aluno/professor genérico: cada aula acrescenta uma peça ao mesmo banco, e no encontro 24 você entrega esse banco documentado. A Bella Massa é uma pizzaria com delivery e salão, e as duas operações convivem no mesmo modelo — é justamente essa convivência que gera as decisões interessantes.

Este é o destino. Você não precisa entender o diagrama agora; precisa saber que ele existe e que será construído por você, tabela por tabela, a partir do encontro 04.

São dezessete tabelas. Duas delas costumam surpreender quem já viu exercícios de pizzaria em outros cursos:

  • produto_tamanho_preco — porque o preço não é da pizza, é da pizza naquele tamanho. Broto e família custam diferente e são o mesmo produto.
  • bina — o identificador de chamadas. O plano de ensino cita explicitamente a identificação de quem está ligando, e esse requisito gera uma decisão de modelagem fina: a ligação é registrada antes de se saber se o número pertence a um cliente cadastrado.

Para dar o gosto do que vem: esta é uma das consultas que você escreverá no encontro 19, respondendo à pergunta que hoje a pizzaria não consegue responder. Não tente entendê-la linha a linha ainda — repare só que uma pergunta de negócio vira uma consulta.

Dado, informação e conhecimento

Três palavras que o dia a dia usa como sinônimos e que, aqui, significam coisas diferentes. A distinção não é filosófica: ela decide o que vai para dentro do banco e o que é produzido na hora da consulta.

Termo Definição Na Bella Massa
Dado Fato bruto, sem contexto. Isolado, não responde nada. 54.90 · 2026-03-14 · Calabresa
Informação Dado com contexto e relação, que responde a uma pergunta. "Em 14/03/2026 vendemos 3 calabresas grandes, somando R$ 164,70."
Conhecimento Informação acumulada que sustenta uma decisão. "Calabresa responde por 38% do faturamento; nunca deixar faltar."

O banco de dados guarda dado. A informação é produzida no momento da consulta, e o conhecimento é construído por quem lê o relatório. Guarde essa hierarquia: ela explica por que não se guarda o total do pedido como se fosse um fato — ele é derivado da soma dos itens, e a aula 05 vai chamá-lo de atributo derivado.

Por que não resolver com planilha

A pergunta é legítima e merece resposta técnica, não desdém. A planilha da Bella Massa funcionou por três anos. O que ela não faz aparece quando o negócio cresce, e são quatro problemas com nome próprio:

Problema Como aparece na planilha Como o banco resolve
Redundância O nome e o telefone do cliente repetidos em cada uma das 400 linhas de pedido dele O cliente é gravado uma vez; o pedido só guarda a referência a ele
Inconsistência "Helena Duarte", "Helena duarte" e "H. Duarte" convivendo como se fossem três pessoas Um cadastro único, protegido por chave primária e restrição de unicidade
Anomalia de exclusão Apagar o último pedido de um cliente apaga também o endereço dele, que só existia ali Cliente e pedido são tabelas separadas; excluir um não destrói o outro
Concorrência Dois atendentes com o arquivo aberto ao mesmo tempo; o último a salvar apaga o trabalho do outro Transações e bloqueios: o SGBD serializa as escritas e nenhuma se perde

Os três primeiros voltam com nome técnico e tratamento formal no encontro 10, sobre normalização. O quarto é assunto do encontro 24. Mas o exemplo mais direto de tudo isso é o que a planilha simplesmente não sabe fazer: recusar um dado inválido. Nenhuma célula do Excel devolve isto:

O que um SGBD faz por você

SGBD é Sistema Gerenciador de Banco de Dados: o software que administra o banco. SQL Server, MySQL, PostgreSQL e Oracle são SGBDs. Ele não é o banco — é quem cuida dele. Estas são as seis responsabilidades que você deixa de programar por conta própria ao usar um:

Função O que o SGBD garante Encontro
Persistência Os dados sobrevivem ao desligamento da máquina, gravados em arquivo próprio 02 e 13
Integridade Regras declaradas uma vez são cobradas em toda escrita, venha ela de onde vier 10 e 14
Concorrência Vários usuários escrevendo ao mesmo tempo sem sobrescrever uns aos outros 15 e 24
Segurança Cada login enxerga e altera apenas o que lhe foi concedido 24
Recuperação Backup, restauração e log de transações para voltar de uma falha 24
Desempenho Índices e otimizador de consultas escolhendo o caminho mais barato 21
Três nomes que não são sinônimos

Banco de dados é a coleção organizada de dados — no nosso caso, o BELLAMASSA, com suas dezessete tabelas.

SGBD é o programa que gerencia esse banco — no nosso caso, o Microsoft SQL Server 2022 Express.

SQL é a linguagem com que você fala com o SGBD. Ela é padronizada (ANSI/ISO), mas cada produto tem o seu dialeto: o do SQL Server chama-se T-SQL. Trocar esses três nomes é o erro de vocabulário mais comum da unidade, e ele aparece em prova.

Comece a pasta do projeto hoje

Crie agora uma pasta projeto-bellamassa com quatro subpastas: requisitos, modelagem, scripts e documentacao. Cada encontro produz um arquivo que vai para uma delas. Quem monta a entrega final no último dia sempre descobre que perdeu a versão boa do diagrama.

Classifique cada item como dado, informação ou conhecimento, e justifique em uma linha:

  1. (11) 98877-1122
  2. "O cliente Rafael Nunes pediu 2 calabresas família em 14/03/2026, total R$ 109,80."
  3. 2026-03-14
  4. "Sexta-feira fatura o dobro de terça, então a escala de entregadores precisa dobrar."
Ver gabarito
  1. Dado. Um número isolado; sem contexto não se sabe nem de quem é.
  2. Informação. Reúne cliente, produto, quantidade, data e valor — responde "o que aconteceu naquele dia".
  3. Dado. Uma data solta não responde nada.
  4. Conhecimento. É um padrão extraído de muitas informações, e já sustenta uma decisão operacional.

Para cada situação, aponte o indicador da UC que ela avalia:

  1. Você habilita o TCP/IP e fixa a porta 1433 na instância.
  2. Você entrega um DER em pé-de-galinha com as cardinalidades marcadas.
  3. Você carrega 2.000 pedidos antigos a partir de um arquivo CSV.
  4. Você restaura o banco a partir do backup de ontem depois de um DELETE sem WHERE.
  5. Você escreve a consulta de faturamento por categoria.
Ver gabarito
  1. Indicador 2 — instala e configura o SGBD.
  2. Indicador 1 — elabora diagramas conforme os requisitos.
  3. Indicador 4 — importa e exporta dados.
  4. Indicador 5 — executa backup e restauração.
  5. Indicador 3 — desenvolve scripts SQL coerentes com o modelo.

A gestora pergunta: "por que eu vou gastar com isso se a planilha funciona?". Escreva quatro argumentos técnicos, um para cada problema estudado, usando um exemplo concreto da pizzaria em cada um.

Ver gabarito
  • Redundância: o telefone da Helena está repetido em 412 linhas. Se ela mudar de número, são 412 células para corrigir — e basta esquecer uma.
  • Inconsistência: "Calabresa", "calabreza" e "Calabresa G" hoje contam como três produtos diferentes, e por isso o relatório do contador não fecha.
  • Anomalia de exclusão: ao apagar a linha do único pedido de um cliente, o endereço dele desaparece junto, porque só existia naquela linha.
  • Concorrência: na sexta à noite dois atendentes anotam pedidos ao mesmo tempo; quem salvar por último sobrescreve os pedidos do outro.

Sem entrevistar ninguém ainda, e só a partir do que você leu sobre a Bella Massa, escreva cinco regras de negócio no formato "Todo/Cada X ..." ou "Um X pode ...". Guarde este papel: no encontro 04 você vai confrontá-lo com a entrevista real da gestora.

Ver gabarito comentado

Não existe uma resposta única. Cinco regras defensáveis a partir do texto desta aula:

  1. Todo pedido pertence a exatamente um cliente.
  2. Um pedido pode conter vários produtos, e um produto aparece em vários pedidos.
  3. Cada produto tem um preço diferente para cada tamanho em que é vendido.
  4. Um pedido de delivery gera uma entrega; um pedido de salão ocupa uma mesa.
  5. Toda ligação recebida é registrada, mesmo quando o número não é de cliente cadastrado.

Se as suas cinco regras usam substantivos (cliente, pedido, produto, tamanho, mesa, entrega), você já encontrou as primeiras entidades — que é exatamente o que o encontro 04 vai formalizar.

Para cada dúvida abaixo, diga em qual encontro ela será respondida. Use a barra lateral ou a busca do site.

  1. "Como eu garanto que ninguém cadastre o mesmo CPF duas vezes?"
  2. "Como eu descubro quais clientes nunca pediram nada?"
  3. "Como eu registro automaticamente quem mudou o preço de uma pizza?"
  4. "Como eu volto o banco ao estado de ontem à noite?"
Ver gabarito
  1. Encontro 14 — constraints UNIQUE e CHECK.
  2. Encontro 19 — LEFT JOIN, ou encontro 20 com NOT EXISTS.
  3. Encontro 23 — trigger de auditoria com as tabelas inserted e deleted.
  4. Encontro 24 — RESTORE e modelos de recuperação.

O objetivo do exercício não é a resposta: é você perceber que toda dúvida prática do curso já tem endereço na trilha.

Erros comuns

Conceito Chamar o SGBD de "banco de dados"

"Vou instalar um banco de dados" e "o Excel é um banco de dados" são as duas frases que denunciam a confusão. Instalar, você instala o SGBD; o banco você cria depois, com um comando. E o Excel é uma planilha eletrônica: guarda dados, mas não oferece nenhuma das seis funções da tabela acima.

Correção: use a frase de teste — "o SQL Server 2022 Express (SGBD) gerencia o banco BELLAMASSA (banco de dados), e eu falo com ele em T-SQL (linguagem)". Se a sua frase não couber nesse molde, algum dos três nomes está no lugar errado.
Msg 911 Achar que instalar o SGBD já cria o banco

Consequência direta do erro anterior. Terminada a instalação, existem apenas os bancos de sistema (master, model, msdb, tempdb). O banco do projeto não existe até você criá-lo, e isso só acontece no encontro 13.

Correção: depois de instalar, liste o que existe com SELECT name FROM sys.databases; — você verá os quatro bancos de sistema e mais nada. O encontro 03 faz exatamente essa verificação.
Método Começar o projeto pelo CREATE TABLE

É a tentação de quem já viu SQL antes: abrir o editor e começar a criar tabelas "enquanto o modelo não fica pronto". O resultado é sempre o mesmo — o diagrama entregue no fim é desenhado a partir das tabelas, para justificar o que já existe, e deixa de ser um projeto para virar uma legenda.

É também o caminho mais rápido para perder nota no indicador 1, porque a incoerência entre diagrama e banco fica visível na primeira conferência.

Correção: respeite a ordem da unidade — requisito (04), modelo conceitual (05 a 07), modelo lógico (08 a 10), dicionário (11) e só então DDL (13). Nenhum CREATE TABLE antes do encontro 13, nem por curiosidade.
Conceito Confundir SQL com SQL Server

"Eu sei SQL Server" e "eu sei SQL" dizem coisas diferentes. SQL é a linguagem padronizada; SQL Server é um produto da Microsoft que a implementa com extensões próprias — o T-SQL. MySQL, PostgreSQL, Oracle e SQLite também falam SQL, com dialetos distintos.

O núcleo (SELECT, JOIN, GROUP BY) é praticamente o mesmo em todos. As diferenças aparecem em funções de data, limitação de linhas (TOP no T-SQL, LIMIT no MySQL e no PostgreSQL) e em tudo que é procedural.

Correção: aprenda o padrão e saiba o que é dialeto. Este curso marca explicitamente, em nota, sempre que um comando for específico do T-SQL — assim você leva a competência para qualquer SGBD.
